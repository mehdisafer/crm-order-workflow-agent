## Second regression identified by the real browser exercise

The next release-candidate [push run 43768839560](https://github.com/mehdisafer/crm-order-workflow-agent/actions/runs/43768839560) and [PR run 43768907717](https://github.com/mehdisafer/crm-order-workflow-agent/actions/runs/43768907717) passed the core and Temporal jobs, and successfully launched the GitHub runner's Chrome 157. The reference HTTP smoke again completed before the UI exercise. The browser then timed out after 90 seconds waiting for `Awaiting approval`, with zero browser page/console/HTTP errors. The saved [push-run artifact](https://github.com/mehdisafer/crm-order-workflow-agent/actions/runs/43768839560) reports `locator.waitFor: Timeout 90000ms exceeded`.

The worker logs show the second case reached `prepare` and then emitted a terminal notification rather than an approval. The two test helpers shared the same default request target: `deploy/reference_smoke.py` sets the synthetic order date to **today + 10 days**, and `deploy/capture_operator.mjs` previously submitted **today + 10 days** again. The server correctly rejects an unchanged target with `NO_CHANGE_NEEDED`, so no approval is expected. This is a test-harness sequencing defect, not proof of a duplicate write or an application permission failure.

The corrective browser exercise now reads the actual authenticated case queue, extracts the current observed date of `ORD-1001`, chooses a future target distinct from those observed dates, and records the date-selection evidence. An explicitly supplied `--requested-date` is still honored. The business `NO_CHANGE_NEEDED` guard is unchanged. The new source must itself be requalified.
